# 웹 백엔드 개발자가 대충 넘어가는 문제들 — 2편: 백엔드·DB (Java/Spring)

> AI가 고쳐준 에러 아래에서 이해 없이 지나치기 쉬운 지점들을 모은 시리즈의 2편이다. 시리즈 소개와 읽는 법은 1편에 있다.
>
> 2편은 서버 안쪽, 트랜잭션·JPA·DB다. AI가 "인덱스 하나 추가하면 됩니다"로 덮고 지나가는 영역이다.

**2편의 지도**

- **1~5번은 동시성과 유한한 자원이다.** 여러 요청이 같은 데이터를 동시에 만질 때 벌어지는 일, 그리고 그 트랜잭션이 커넥션을 쥐고 있다는 사실을 다룬다.
- **6~7번은 JPA의 숨은 상태 기계다.** `save()` 없이 UPDATE가 나가는 것도, 직렬화 중에 쿼리가 터지는 것도 여기서 나온다.
- **8~10번은 데이터가 많아질 때 드러나는 성능 함정이다.**

## 1. `@Transactional` — 붙였는데 왜 롤백이 안 되지?

**반창고**: 서비스 메서드에 `@Transactional`을 뿌려두고 "트랜잭션 처리됨"이라 가정.

**실제로는**

전부 에러 없이 그냥 안 되는 유형이라 더 위험하다.

- **자기 호출**: 같은 빈 안에서 `this.inner()`로 부르면 프록시를 거치지 않아 트랜잭션이 걸리지 않는다.
  ```java
  public void outer() { this.inner(); }       // 트랜잭션 X
  @Transactional public void inner() { ... }  // 외부에서 호출돼야만 적용
  ```
- **체크 예외**: 기본 롤백 대상은 `RuntimeException`과 `Error`뿐이라 체크 예외에선 커밋된다. "예외를 던졌는데 왜 저장됐지?"의 정체이며, 필요하면 `rollbackFor = Exception.class`를 준다.
- **private 메서드**: 프록시가 오버라이드할 수 없어 `@Transactional`이 무시된다. Spring 6 이전엔 `public`이 아니면 전부 무시됐다.
- `readOnly`와 전파 옵션도 의미를 알고 써야 한다. 특히 `REQUIRES_NEW`는 커넥션을 하나 더 잡으므로 5번 커넥션 풀과 엮인다.

**핵심 한 줄**: `@Transactional`은 프록시 기반이라 **자기 호출, 체크 예외, private 메서드**에서 에러 없이 무력화된다.

## 2. 격리 수준 — 로컬 MySQL에선 됐는데 운영 PostgreSQL에선 왜?

**반창고**: `@Transactional`만 붙이고 격리 수준은 한 번도 의식하지 않음.

**실제로는**

격리 수준은 동시에 도는 트랜잭션이 서로를 얼마나 보는가이고, 세 가지 이상현상을 어디까지 막느냐로 나뉜다.

- **Dirty Read**: 커밋 안 된 남의 변경을 읽음
- **Non-repeatable Read**: 같은 행을 두 번 읽었는데 값이 바뀜. 중간에 남이 커밋한 경우다.
- **Phantom Read**: 같은 조건으로 두 번 조회했는데 행 개수가 바뀜. 중간에 남이 INSERT한 경우다.

| 격리 수준 | Dirty | Non-repeatable | Phantom |
|---|---|---|---|
| READ UNCOMMITTED | 허용 | 허용 | 허용 |
| READ COMMITTED | 방지 | 허용 | 허용 |
| REPEATABLE READ | 방지 | 방지 | 허용* |
| SERIALIZABLE | 방지 | 방지 | 방지 |

가장 많이 놓치는 것은 **DB마다 기본값이 다르다**는 점이다.

- MySQL(InnoDB)은 REPEATABLE READ다. 게다가 next-key 락 덕에 표준과 달리 팬텀까지 대부분 막는다. 표의 `*`가 이것이다.
- PostgreSQL은 READ COMMITTED다.

같은 코드가 두 DB에서 다르게 동작할 수 있다는 뜻이고, 로컬과 운영의 DB가 다르면 이것이 숨은 원인이 되기도 한다.

**핵심 한 줄**: `@Transactional`을 붙인 순간 이미 **DB 기본 격리 수준(MySQL=RR, PostgreSQL=RC)** 위에서 돌고 있다는 걸 알아야 한다.

## 3. 갱신 손실 — 트래픽이 몰리면 재고 숫자가 안 맞는다

**반창고**: 잔액·재고·좋아요 수를 `조회 → 계산 → 저장`으로 처리.

**실제로는**

두 요청이 동시에 같은 행을 읽고, 수정하고, 쓰면 나중 쓰기가 먼저 쓰기를 덮어쓴다. 재고 100에서 두 명이 동시에 1개씩 사면 99가 두 번 쓰여 **하나가 증발**한다. 에러는 나지 않고 데이터만 조용히 틀어진다. 이런 애플리케이션 레벨의 read-modify-write 경합은 격리 수준만으로는 대개 막히지 않는다.

**제대로** — 세 가지 무기

- **원자적 UPDATE**: 읽지 말고 DB가 계산하게 한다. `UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0`이 가장 단순하고 안전하다.
- **낙관적 락**: 엔티티에 `@Version`을 두면 JPA가 `UPDATE ... WHERE version = ?`로 갱신하고, 버전이 어긋나면 `OptimisticLockException`을 던진다(Spring에선 `ObjectOptimisticLockingFailureException`). 충돌이 드물 때 재시도 로직과 함께 쓴다.
  ```java
  @Entity class Account {
      @Version private Long version; // 이 한 줄이 낙관적 락
  }
  ```
- **비관적 락**: `SELECT ... FOR UPDATE`로 행을 잠그고 작업한다. Spring Data에선 `@Lock(LockModeType.PESSIMISTIC_WRITE)`이고, 충돌이 잦거나 정합성이 절대적일 때 쓴다.

**핵심 한 줄**: 동시성 아래서 `조회→수정→저장`은 데이터를 조용히 잃으니, **원자적 UPDATE, `@Version`, `FOR UPDATE`** 중 하나로 막아라.

## 4. 데드락 — 같은 행을 건드린 적이 없는데 왜 데드락이지?

**반창고**: 가끔 `Deadlock found` 에러가 나면 그냥 재시도. 원인은 안 봄.

**실제로는**

- 데드락은 보통 **두 트랜잭션이 자원을 반대 순서로 잠글 때** 생긴다. A가 1번→2번 행을, B가 2번→1번 행을 잠그려 하면 서로 영원히 기다린다.
- 안 건드린 행끼리도 충돌할 수 있다. InnoDB는 REPEATABLE READ에서 팬텀을 막으려고 존재하지 않는 행 사이의 틈까지 잠그는 **gap 락과 next-key 락**을 쓰고, 그래서 범위만 겹쳐도 데드락이 난다.

**제대로**

- **잠그는 순서를 일관되게 한다.** 여러 행을 잠글 땐 항상 id 오름차순처럼 같은 순서로 접근하면 순서 역전 데드락은 사라진다.
- **트랜잭션을 짧게 유지한다.** 락을 쥔 채 외부 API를 부르거나 무거운 연산을 하면 락 보유 시간만큼 충돌 확률이 오른다.
- 데드락은 완전히 없애기 어려우니 짧은 재시도를 두되, `SHOW ENGINE INNODB STATUS`로 원인을 확인한 뒤의 재시도와 무지성 재시도는 다르다.

**핵심 한 줄**: 데드락은 대개 락 순서 역전에서 오니, **항상 같은 순서로 잠그고** 트랜잭션을 짧게 유지하라.

## 5. 커넥션 풀 — 풀을 키웠는데 왜 더 느려지지?

**반창고**: 부하가 걸리거나 `Connection is not available, request timed out`이 나면 HikariCP `maximumPoolSize`를 100, 200으로 키움.

**실제로는**

- **풀은 클수록 빠르지 않다.** DB가 동시에 처리할 수 있는 작업 수는 코어와 디스크로 제한되어, 커넥션이 너무 많으면 컨텍스트 스위칭과 락 경합으로 오히려 느려진다.
- HikariCP가 작은 풀을 권하는 이유다. 기본값은 10이고, 경험칙은 `(코어 수 × 2) + 디스크 수` 수준이다.
- 타임아웃의 진짜 원인은 대개 **느린 쿼리나 긴 트랜잭션이 커넥션을 오래 쥐고 있는 것**이다. 풀을 늘리는 건 증상 가리기이고, 근본 해결은 그 작업을 찾는 것이다.
- 커넥션이 묶이는 흔한 경로는 둘이다. 트랜잭션 안에서 외부 API를 호출하는 것, 그리고 7번의 OSIV처럼 요청이 끝날 때까지 붙들고 있는 것이다.
- 풀 크기는 DB의 `max_connections`를 넘으면 안 된다. 인스턴스가 여러 대면 인스턴스 수 × 풀 크기가 그 한도 안이어야 한다.

**핵심 한 줄**: 커넥션 타임아웃은 풀이 작다는 신호가 아니라 **누군가 커넥션을 오래 쥐고 있다는 신호**다.

## 6. 영속성 컨텍스트 — `save()`를 안 했는데 왜 UPDATE가 나가지?

**반창고**: JPA를 객체로 쓰는 SQL 정도로 여기고, 언제 쿼리가 나가는지 감으로 씀.

**실제로는**

멘탈 모델 세 조각이 빠져 있어서 그렇다.

- **변경 감지**: 영속성 컨텍스트는 조회한 엔티티의 스냅샷을 들고 있다가, flush 시점에 현재 값과 비교해 바뀐 필드의 UPDATE를 자동 생성한다. 그래서 트랜잭션 안에서 조회한 엔티티는 필드만 바꿔도 `save()` 없이 UPDATE가 나가고, 반대로 준영속(detached) 엔티티는 아무리 바꿔도 반영되지 않는다.
- **flush 타이밍**: SQL은 트랜잭션 커밋 직전과 JPQL 쿼리 실행 직전에 모아서 나간다. 코드 순서와 실제 SQL 순서가 달라 보이는 이유다.
- **`persist`와 `merge`**: `persist`는 새 엔티티를 영속화하고, `merge`는 준영속 엔티티의 상태를 복사한 새 관리 객체를 반환한다. 흔한 버그는 `merge(entity)` 뒤에 반환값 대신 인자로 넘긴 원본을 계속 쓰는 것인데, 원본은 여전히 준영속이라 변경이 반영되지 않는다.

**핵심 한 줄**: `save()` 없이 나가는 UPDATE도, 씹히는 변경도 전부 **변경 감지·flush 타이밍·영속 상태**라는 숨은 상태 기계에서 나온다.

## 7. N+1과 지연 로딩 — 목록 API 하나에 쿼리가 수백 개

**반창고**: `LazyInitializationException`이 나길래 fetch를 `EAGER`로 바꾸거나, 컨트롤러에 `@Transactional`을 붙여 회피.

**실제로는**

- 엔티티 N개를 불러온 뒤 지연 연관을 건드리면, 연관을 채우려 N번의 추가 쿼리가 나간다. 이것이 **N+1**이고, 목록 API에서 조용히 수백 개 쿼리가 나가는 주범이다.
- `EAGER`로 바꾸면 그 연관이 항상 끌려와 **전역적으로 더 나빠진다.** 반창고가 문제를 키우는 대표 사례다.
- `LazyInitializationException`은 영속성 컨텍스트가 닫힌 뒤에 지연 필드를 건드릴 때 난다. 대표적으로 직렬화 단계다.
- Spring Boot는 **`spring.jpa.open-in-view`(OSIV)가 기본 `true`**라 이 예외가 가려진다. 그 대가로 DB 커넥션을 요청 끝까지 붙들고(5번) 직렬화 중에 N+1을 유발하는데, 이 기본값을 모르는 사람이 정말 많다.

**제대로**

```java
// fetch join: 연관까지 한 번에
@Query("select o from Order o join fetch o.items where o.id = :id")
Optional<Order> findWithItems(@Param("id") Long id);
```

- fetch join 외에 `@EntityGraph`, `@BatchSize`도 있다. 응답엔 엔티티 대신 DTO 프로젝션을 쓴다.
- 단, **컬렉션 fetch join에 페이징을 걸면** Hibernate는 경고 로그 한 줄만 남기고 전체를 메모리로 가져와 자른다. 목록 페이징엔 `@BatchSize`나 `default_batch_fetch_size`가 맞다.
- 무엇보다 SQL 로그를 켜서 실제 쿼리 수를 세는 습관이 중요하다.

**핵심 한 줄**: 지연 로딩 예외를 `EAGER`나 `@Transactional`로 덮지 말고, **쿼리 로그를 보며 fetch join이나 DTO로** 풀어라.

## 8. 인덱스 — 인덱스를 걸었는데 왜 안 빨라지지?

**반창고**: 쿼리가 느리길래 해당 컬럼에 인덱스를 추가하고 끝. AI가 던져준 `CREATE INDEX`를 그대로 적용.

**실제로는**

- 대부분의 인덱스는 정렬된 트리인 B-tree다. `=`, 범위, `ORDER BY`, 앞부분 일치(`LIKE 'abc%'`)엔 강하지만 **뒷부분 일치(`LIKE '%abc'`)엔 무력하다.**
- **복합 인덱스는 컬럼 순서가 전부다.** `(a, b, c)` 인덱스는 `a`, `a+b`, `a+b+c` 조건엔 쓰이지만 `b`만, `c`만으로는 타지 않는다. 이를 leftmost prefix 규칙이라 한다.
- 인덱스가 조용히 무시되는 경우도 있다.
  - 인덱스 컬럼을 함수로 감쌈: `WHERE YEAR(created) = 2026`
  - 타입 불일치로 인한 암묵적 형변환: varchar인 `phone`을 `WHERE phone = 01012345678`처럼 숫자와 비교
  - 선두 와일드카드: `LIKE '%x'`
  - 너무 낮은 카디널리티: 성별 컬럼처럼 값 종류가 적으면 옵티마이저가 인덱스를 포기한다

**제대로**

- **`EXPLAIN`을 읽는다.** MySQL 기준으로 `type`이 `ALL`이면 풀스캔이고, `rows`는 예상 스캔 행수, `Extra`의 `Using filesort`나 `Using temporary`는 정렬이나 임시 테이블이 생긴다는 뜻이다. 인덱스는 추측으로 거는 게 아니라 실행계획으로 검증하는 것이다.
- **커버링 인덱스**: 쿼리에 필요한 컬럼을 인덱스가 모두 포함하면 테이블 접근 없이 인덱스만으로 끝나고, `Extra`에 `Using index`로 나온다.
- 인덱스는 읽기를 빠르게 하는 대신 **쓰기를 느리게** 한다. 무한정 추가하면 안 되는 이유다.

**핵심 한 줄**: 인덱스는 거는 게 아니라 **`EXPLAIN`으로 검증**하는 것이고, 안 탄다면 컬럼 순서와 함수·형변환·선두 와일드카드부터 의심하라.

## 9. 페이지네이션 — 뒤 페이지로 갈수록 왜 느려지지?

**반창고**: `LIMIT 20 OFFSET 100000`으로 페이징.

**실제로는**

`OFFSET 100000`은 앞의 10만 행을 **실제로 읽어서 버린 뒤** 다음 20개를 준다. 페이지가 깊어질수록 버리는 양이 늘어 선형으로 느려지고, 무한 스크롤이나 대용량 목록에서 치명적이다.

**제대로** — 커서(키셋) 페이지네이션

직전 페이지의 마지막 값을 기준으로 자른다.

```sql
SELECT * FROM posts WHERE id < :lastSeenId ORDER BY id DESC LIMIT 20
```

인덱스를 타고 버리는 행 없이 다음 구간으로 바로 점프하므로, 몇 번째 페이지든 일정하게 빠르다. 단점은 임의의 N페이지로 점프할 수 없다는 것이다. 정렬 기준이 유일하지 않으면 `(created, id)` 같은 복합 커서를 쓴다.

**핵심 한 줄**: `OFFSET`은 앞 행을 전부 읽고 버리므로, 깊은 페이지가 필요한 목록엔 **커서 페이지네이션**을 써라.

## 10. 벌크 연산 — `saveAll()`로 1만 건, 왜 이렇게 느리지?

**반창고**: 1만 건을 `repository.saveAll(list)`로 저장하고, 느리면 원래 그런가 보다 하고 넘어감.

**실제로는**

- `saveAll`은 내부적으로 **건건이 `save`를 도는** 것이다.
- ID를 직접 할당한 엔티티라면 `save`가 새 엔티티인지 판단하지 못해 `merge`로 빠지고, 건마다 SELECT가 하나씩 더 나간다. `Persistable`을 구현해 새 엔티티 여부를 알려주면 해결된다.
- JDBC 배치도 자동으로 켜지지 않는다. `hibernate.jdbc.batch_size`를 설정하고, MySQL이면 JDBC URL에 `rewriteBatchedStatements=true`까지 줘야 INSERT가 실제로 묶여 나간다.
- 더 근본적인 함정은 **`IDENTITY` 전략이면 INSERT 배치가 아예 불가능**하다는 것이다. INSERT를 실행해야 ID를 알 수 있어 Hibernate가 묶지 못한다.
- 대량 INSERT가 중요하면 `SEQUENCE` 전략과 pooled optimizer를 쓰거나 `JdbcTemplate.batchUpdate`로 내려간다.
- 반대로 JPQL 벌크 연산(`@Modifying`의 UPDATE/DELETE)은 영속성 컨텍스트를 **우회**해 DB에 바로 적용된다. 그래서 1차 캐시엔 옛날 값이 남아, 같은 트랜잭션에서 다시 조회하면 stale 데이터가 나온다.
- 이땐 `@Modifying(flushAutomatically = true, clearAutomatically = true)`로 컨텍스트를 비운다. flush 없이 clear만 하면 아직 반영되지 않은 변경까지 날아간다.

**핵심 한 줄**: `saveAll`은 설정 없이는 배치가 아니고, **`IDENTITY` 전략이면 설정해도 배치가 안 된다.**

## 짧게 짚고 가는 것들

- **운영 DB 스키마 변경**: 큰 테이블의 `ALTER`는 테이블을 잠그거나 전체를 재작성할 수 있다. "컬럼 하나 추가인데 설마"가 장애가 되는 전형이다. MySQL 8의 online DDL(`ALGORITHM=INSTANT/INPLACE`) 가능 여부를 확인하고, 마이그레이션은 Flyway나 Liquibase로 코드처럼 버전 관리한다.
- **MySQL `utf8`은 가짜다**: 실체는 `utf8mb3`라 이모지를 저장하지 못하고, 진짜 UTF-8은 `utf8mb4`다. DB·테이블·커넥션(JDBC `characterEncoding`)까지 일관되게 맞추고, 조인 컬럼의 콜레이션이 다르면 에러가 나거나 인덱스를 못 탄다.

---

> **공통 교훈**: DB는 증상(느림·데드락·숫자 불일치)과 원인(실행계획·락 순서·격리 수준)이 멀리 떨어져 있다. `EXPLAIN`을 읽고, 격리 수준을 알고, 동시성을 의심하는 세 습관만 들여도 "원인 모를 문제" 대부분이 설명 가능해진다.
