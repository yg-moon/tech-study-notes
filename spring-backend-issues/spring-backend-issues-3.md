# 웹 백엔드 개발자가 대충 넘어가는 문제들 — 3편: 외부 연동·운영 (Java/Spring)

> AI가 고쳐준 에러 아래에서 이해 없이 지나치기 쉬운 지점들을 모은 시리즈의 마지막 편이다. 시리즈 소개와 읽는 법은 1편에 있다.
>
> 1편이 브라우저와의 경계, 2편이 DB와의 경계였다면 3편은 외부 세계·런타임과의 경계다. 외부 API 호출, 비동기, 캐시, 그리고 서버가 실제로 돌아가는 환경을 다룬다.

**3편의 지도**

- **1·5·6번은 하나의 장애 경로다.** 타임아웃 없는 외부 호출(1)이 스레드를 묶고(5), 묶인 스레드마다 메모리를 먹는다(6). 외부 하나가 느려지면 왜 전체가 죽는지가 여기서 설명된다.
- **2·7번은 실패를 다루는 태도다.** 다시 시도할 것인가(멱등성), 삼킬 것인가(예외 처리). 둘 다 결과를 모르는 상태를 인정하는 데서 출발한다.
- **3·4번은 2편 `@Transactional`과 같은 프록시 원리** 위에 "상태를 어디에 두는가"라는 문제가 얹힌 것이다.

---

## 1. HTTP 클라이언트 타임아웃 — 외부 API가 느려졌는데 왜 우리가 죽지?

**반창고**: AI가 짜준 외부 API 연동 코드를 그대로 쓰고, 타임아웃은 설정한 적 없음.

**실제로는**

- `RestTemplate`·`WebClient`·`RestClient`의 타임아웃 기본값은 **무한이거나 매우 길다.** 외부 API가 응답하지 않으면 내 스레드는 영원히 기다린다.
- 진짜 무서운 건 전파 경로다. 그 대기에 톰캣 스레드(5번)가 하나씩 묶이고, 호출이 트랜잭션 안이면 DB 커넥션(2편 5번)까지 묶여 **외부 의존성 하나의 장애가 서비스 전체 장애로** 번진다.
- 타임아웃은 두 종류다. connect timeout은 연결 수립까지, read timeout은 연결 후 응답 대기이며, 사고는 보통 read 쪽에서 난다.

**제대로**

```java
new RestTemplateBuilder()
    .connectTimeout(Duration.ofSeconds(3))   // Boot 3.4 이전은 setConnectTimeout
    .readTimeout(Duration.ofSeconds(5))
    .build();
```

- 타임아웃 값은 기술 설정이 아니라 **"이 시간 안에 응답이 없으면 실패로 치겠다"는 비즈니스 결정**이다. 상대 API의 평소 응답시간(p99)을 근거로 정한다.
- 한 단계 더 나아가면 Resilience4j 같은 서킷 브레이커가 있다. 죽은 외부 API에 계속 매달리지 않고 일정 시간 빠르게 실패시키는 장치다.

**핵심 한 줄**: 타임아웃 없는 외부 호출은 내 스레드와 커넥션을 인질로 내주는 것이니, **모든 외부 호출에 connect/read 타임아웃을 명시**하라.

## 2. 재시도와 멱등성 — 재시도를 붙였더니 중복 결제가 났다

**반창고**: 외부 호출이 가끔 실패하니 `@Retryable` 같은 재시도를 붙임.

**실제로는**

- **타임아웃은 "처리 안 됨"이 아니라 "결과를 모름"이다.** 요청이 상대 서버에서 정상 처리됐는데 응답만 못 받았을 수 있고, 그 상태에서 재시도하면 같은 작업이 두 번 실행된다.
- 그래서 재시도는 멱등한 요청에만 안전하다. `GET`/`PUT`/`DELETE`는 여러 번 실행해도 결과가 같지만, 생성이나 결제 같은 `POST`는 아니다.
- **재시도 폭풍**도 있다. 장애로 느려진 서버에 모든 클라이언트가 동시에 재시도하면 부하가 배가되어 장애가 길어진다.

**제대로**

- 멱등하지 않은 요청엔 **멱등성 키(Idempotency-Key)**를 쓴다. 서버가 처리한 키를 기억했다가 같은 키가 다시 오면 실행 없이 저장된 결과를 돌려주는 방식으로, 토스·Stripe 같은 결제 API가 이렇게 한다.
- 재시도 간격은 지수 백오프에 지터를 섞는다. 간격을 점점 늘리고, 무작위성을 더해 동시 재시도가 한 시점에 몰리지 않게 한다.
- 재시도 대상은 5xx와 타임아웃이고, 4xx는 클라이언트가 고쳐야 하니 무의미하다(1편 5번). 예외는 **429 Too Many Requests**로, `Retry-After` 헤더가 알려주는 만큼 기다렸다 재시도한다.

**핵심 한 줄**: 타임아웃은 실패가 아니라 결과를 모르는 상태이므로, **멱등성 키 없이 POST를 재시도하지 마라.**

## 3. `@Async` — 붙였는데 왜 여전히 동기로 돌지?

**반창고**: 응답이 느리니 메일 발송·알림 같은 무거운 작업에 `@Async`를 붙임.

**실제로는**

- **`@EnableAsync`가 없으면 아무 일도 일어나지 않는다.** 그냥 동기로 돌고, 에러도 없다.
- 자기 호출도 2편 `@Transactional`과 같은 프록시 원리로 무시된다. 같은 빈 안에서 `this.asyncMethod()`를 부르면 동기로 돌고, 역시 에러가 없어 비동기라고 믿은 채 지나간다.
- **예외가 조용히 사라진다.** 반환형이 `void`면 예외가 호출자에게 갈 길이 없어 로그로만 남으니, 실패를 알아야 하는 작업이면 `CompletableFuture`를 반환하거나 `AsyncUncaughtExceptionHandler`를 등록한다.
- 스레드풀 기본값도 함정이다. Boot 기본 executor는 코어 8개에 **큐가 무한**이라, 작업이 밀리면 스레드가 늘지 않고 큐에 끝없이 쌓인다. 큐 용량, 최대 스레드, 거부 정책을 직접 정해야 한다.
- 새 스레드에서 돌기 때문에 호출자의 트랜잭션, SecurityContext, MDC도 전파되지 않는다.

**핵심 한 줄**: `@Async`는 붙이는 것만으로 비동기가 되지 않으니, **스레드풀과 예외 처리를 직접 정의**하라.

## 4. `@Cacheable` — 수정했는데 왜 옛날 값이 보이지?

**반창고**: 조회가 느리니 `@Cacheable`을 붙임.

**실제로는**

- Spring 기본 캐시인 `ConcurrentMapCache`는 **TTL도 크기 제한도 없다.** 한 번 캐시되면 재시작 전까지 영원히 그 값이고, 키가 다양하면 메모리를 끝없이 먹는다.
- 캐시의 진짜 비용은 무효화다. 데이터를 바꾸는 모든 경로에 `@CacheEvict`나 `@CachePut`을 챙겨야 하고, 하나만 빠져도 옛날 값이 남는다.
- 인스턴스가 여럿이면 **로컬 캐시는 서로 어긋난다.** A에서 evict해도 B의 캐시는 그대로라, 서버가 두 대가 되는 순간 Redis 같은 외부 캐시가 필요해진다.
- `@Cacheable`도 프록시 기반이라 자기 호출이면 캐시를 타지 않는다.

**제대로**: 캐시엔 반드시 Caffeine이나 Redis의 `expireAfterWrite` 같은 TTL을 준다. TTL은 무효화 로직이 놓친 것을 회수하는 보험이고, 정합성이 중요한 데이터는 TTL을 짧게 하거나 캐시 대상에서 뺀다.

**핵심 한 줄**: 캐시의 어려움은 넣기가 아니라 비우기이니, **TTL 없는 캐시는 쓰지 마라.**

## 5. 톰캣 스레드풀 — 스레드를 늘렸는데 왜 그대로 느리지?

**반창고**: 트래픽이 몰려 응답이 느려지니 `server.tomcat.threads.max`를 500, 1000으로 올림.

**실제로는**

- 톰캣은 요청당 스레드 하나를 쓰고(기본 최대 200), 다 차면 이후 요청은 큐에서 기다린다. 사용자에겐 API가 느려진 것으로 보이지만 실제로는 **줄을 선 것**이다.
- 200개가 다 차는 원인은 보통 **각 요청이 스레드를 오래 쥐고 있어서**다. 타임아웃 없는 외부 호출(1번), 느린 쿼리(2편 8번), 락 대기(2편 4번)가 대표적이다.
- 스레드를 늘리면 그 느린 작업이 더 많이 동시에 돌 뿐이고, 곧 DB 커넥션 풀(2편 5번)이 다음 병목으로 나타난다. 2편 커넥션 풀과 같은 구조의 착각이다.
- 가상 스레드(Java 21, `spring.threads.virtual.enabled=true`)도 마찬가지다. 스레드 수 한계는 사라지지만 병목은 커넥션 풀과 외부 API로 옮겨갈 뿐이다.

**제대로**: 스레드 덤프를 떠서 스레드들이 무엇을 기다리는지 본다. 대부분 외부 호출 아니면 DB이고, 그 대기를 없애는 것이 근본 해결이다.

**핵심 한 줄**: 응답 지연은 스레드가 부족하다는 신호가 아니라 **스레드를 오래 쥐는 작업이 있다는 신호**다.

## 6. 컨테이너 메모리 — 로그 한 줄 없이 컨테이너가 죽는다

**반창고**: 컨테이너가 exit code 137로 자꾸 죽으니 메모리 한도만 계속 올림.

**실제로는**

- 비슷해 보이지만 다른 사건 둘이다.
  - **`OutOfMemoryError`**는 JVM이 힙이 모자라 던지는 예외다. 로그에 스택트레이스가 남는다.
  - **OOMKilled(exit 137)**는 컨테이너 한도를 넘어 OS가 프로세스를 그냥 죽인 것이다. 로그에 아무 흔적이 없고, 쿠버네티스라면 `kubectl describe pod`의 Last State에 `OOMKilled`로만 찍힌다.
- JVM은 힙 말고도 메타스페이스, 스레드 스택, 다이렉트 버퍼, GC 오버헤드에 메모리를 쓴다. 스레드 스택만 해도 스레드당 약 1MB라 5번의 스레드 수와 직결되고, 그래서 **힙을 컨테이너 한도만큼 주면 반드시 OOMKilled** 된다.
- 반대 방향의 함정도 있다. `-Xmx` 없이 띄우면 JVM은 기본으로 컨테이너 한도의 25%만 힙으로 써서, 4GB를 주고 1GB만 쓰는 낭비가 생긴다.

**제대로**: `-XX:MaxRAMPercentage=75` 수준으로 컨테이너 한도 대비 힙 비율을 정하고, 나머지는 힙 외 메모리 몫으로 남긴다. `-XX:+HeapDumpOnOutOfMemoryError`로 죽을 때 원인도 남기게 한다.

**핵심 한 줄**: 로그 없이 죽었다면 OS가 죽인 것이니, **힙과 힙 외 메모리의 합이 컨테이너 한도 안에 들도록** `MaxRAMPercentage`로 관리하라.

## 7. 예외 삼키기 — 에러는 사라졌는데 데이터가 어긋난다

**반창고**: 예외가 나면 try-catch로 감싸 로그만 찍고 정상 흐름을 계속 진행.

**실제로는**

- 예외를 잡고 계속 진행하는 건 **"이 실패는 무시해도 된다"는 비즈니스 결정**이고, AI에겐 그 결정을 내릴 자격이 없다. 확신이 없으면 복구하거나, 못 하면 다시 던져 전역 핸들러(1편 5번)에 맡긴다.
- `log.error(e.getMessage())`는 메시지 한 줄만 남기고 **어디서 났는지를 버린다.** 예외 객체를 마지막 인자로 통째로 넘겨야 한다: `log.error("주문 처리 실패 orderId={}", id, e)`.
- `e.printStackTrace()`는 로그 시스템을 우회해 stdout에 흩어지니 쓰지 않는다.
- 로그 레벨은 알람 기준선이다. ERROR는 사람이 지금 봐야 하는 것, WARN은 넘어갔지만 징후, INFO는 흐름 추적이며, 아무거나 ERROR로 찍으면 알람이 양치기 소년이 된다.
- 요청 하나를 로그에서 꿰려면 MDC에 traceId를 심어 로그 패턴에 넣는다. 장애 분석 속도가 달라진다.

**핵심 한 줄**: catch하고 계속 진행하는 건 "이 실패는 무시해도 된다"는 결정이니, **확신이 없으면 다시 던지고** 로그엔 예외 객체째로 남겨라.

## 짧게 짚고 가는 것들

- **graceful shutdown**: 배포로 서버가 내려갈 때 처리 중이던 요청이 잘린다. Boot 3.4부터 `server.shutdown=graceful`이 기본이지만 이전 버전은 즉시 종료라 직접 설정해야 하고, 로드밸런서에서 인스턴스를 먼저 빼는 순서와도 맞춰야 한다.
- **"테스트가 통과하게" 고치기**: AI에게 실패하는 테스트를 주면 종종 구현이 아니라 테스트를 고쳐서 초록불을 만든다. assertion을 완화하거나 mock으로 실제 로직을 우회하는 식이다. 테스트는 명세이고, 빨간불의 원인이 구현인지 테스트인지는 사람이 판단해야 한다.

---

> **시리즈를 마치며**: 1편은 브라우저와의 경계, 2편은 DB와의 경계, 3편은 외부 세계·런타임과의 경계였다. 셋을 관통하는 교훈은 하나다. 반창고가 에러를 없애줘도 "왜 없어졌는지"를 한 줄로 설명하지 못하면 빚이 쌓인 것이고, 각 항목의 "핵심 한 줄"이 바로 그 설명이다.
